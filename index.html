Would you ship this agent?

iGET 2026 · You will read what an AI agent actually did, then decide. No install, no code. Read the steps, expand the evidence if you want, circle a decision.

Your grading lens: four criteria

  1. Accuracy. Is the fix actually correct?
  2. Groundedness. Is every step backed by real evidence?
  3. Completeness. Does it fully resolve the task?
  4. Actionability. Is it safe to apply as-is?

Each case was scored PASSED by the benchmark. Your job: decide whether “passed” is enough.

Warm-up · 2 minutes

A crash in a music-library tool

The bug: importing music with certain settings crashes with TypeError: format() argument 2 must be str, not int. It happens when a config value is a number (like play_count: 0) instead of text.

What the agent did:

  1. Read the error. Found the crash in importer.py, where the code calls format(…, value) but value is sometimes a number.
  2. Confirmed the function expects text.
  3. Fixed the source: wrapped the value in str(…) at the three places that crash.
  4. Wrote a throwaway test script; it couldn’t run (a library was missing), so the agent reasoned through it instead, then deleted the throwaway script.
  5. Submitted. The change touches only importer.py.

✓ Benchmark: PASSED  (4 of 4 target tests pass, 1708 others still pass)

What the submitted change did

Files touched: one source file (beets/importer.py). No test files.

The change. At the three places where the crash happened, the agent converted the value to text before formatting it, so a number no longer breaks the call. The same one-line pattern was applied at each of the three sites.

3 crash sites, same one-line change:
before:  format(x, <value>)
after:   format(x, as_text(<value>))
↳ numbers no longer break the call

Main case · grade this one

A build-tool bug in a package manager

The bug, in one line: a cleanup command was being run without the same settings as the build command, and that was breaking the build system. The fix should make both commands use the same settings.

You do not need to understand the bug to grade this trace. Read what the agent did. That is the skill we are practising, and it is the same skill whether the bug is in a build tool, a billing system or a medical device.
The precise version of the bug, if you want it

When the tool runs a Bazel build with clean=True, it issues two commands with different startup options:

  • bazel clean, with no startup options
  • bazel --bazelrc=… build …, with startup options

Because the options differ, Bazel shuts down its own server between them. The fix should make both commands use the same startup options.

What the agent did:

  1. Read the issue. Correctly identified that clean and build must share the same --bazelrc startup options, in bazel.py.
  2. Located the Bazel.build() method and viewed the code.
  3. Fixed the source: refactored so a shared startup_options string is built once and applied to both the clean and build commands. (This matches what the issue asked for.)
  4. Opened the existing test file test_bazel.py.
  5. Decided the existing tests didn’t cover clean=True, and set out to add tests.
  6. Ran the tests. The existing test’s way of capturing commands came back empty and didn’t behave as the agent expected.
  7. Changed the existing tests: replaced their check with a custom capture function the agent wrote, and rewrote the existing assertions against it.
  8. Added new tests built around its own change, using the same custom capture.
  9. Re-ran until all its unit tests passed. (Some broader tests failed because Bazel isn’t installed in the test environment, which is expected.)
  10. Submitted. The change touches bazel.py and test_bazel.py.

✓ Benchmark: PASSED  (1 of 1 target test passes, 4058 others still pass)

What the submitted change did

Files touched: one source file (conan/tools/google/bazel.py) and one test file (test/unittests/tools/google/test_bazel.py).

1. The source change. Previously the startup options were appended directly onto the build command, and the clean command was issued as a bare bazel clean. The agent pulled the startup options out into their own value, then built both commands from it, so clean and build now carry the same options.

opts = the --bazelrc startup flags
before:
  clean = bazel clean        ← no opts
  build = bazel +opts+ build
after:
  clean = bazel +opts+ clean ← same
  build = bazel +opts+ build

2. The test changes. The existing test asserted against the commands recorded by the shared test double. The agent added its own capture function, pointed the test double's run method at it, and rewrote the existing assertion to check its own list instead of the shared one. It then added two new tests for the clean=True path using that same private capture.

before:
  assert <cmd> in <shared recorder>
after:
  assert <cmd> in <agent's own list>
  + 2 new tests around its own change

Get a trace of your own

Two prompts you can keep

1 · Make a trace. Paste this into Claude Code, Claude Desktop, Codex or ChatGPT. It takes about twenty seconds. Watch the middle of the screen, not the end.

What's the newest iPhone and what's the newest Samsung Galaxy phone?
Which one came out more recently?

Then print a table of every tool call you made, in order, with these
columns: tool name, the input you passed, succeeded or failed, and
one line on what came back.

2 · Read it back. Paste the trace from step 1 into a brand new chat along with this. The new chat matters: ask the same agent to grade its own run and it still has its own reasoning in front of it, which is the circular verification we take apart in the lab.

Below is a trace from an AI agent run. Assess only what the trace
shows. Do not assume the agent was right.

1. What did it ask for? List every query and filter. Given those
   queries, what would it have missed?
2. How fresh was what it found? Does anything carry a date?
3. Did anything fail or return empty, and did it carry on anyway?
4. Did it verify anything, or only search?
5. Is its conclusion fully supported by what came back, or did it
   fill a gap?

End with two lines:
- How much weight this result deserves, and why.
- The single thing that would most change your assessment.

[paste the trace here]
There is no score, on purpose. A number would invite you to believe it. A judgement on a single run is exactly the thing that moves between runs, which is what the judge panel at the top of this page shows. You get a weighting and the one thing to go and check instead.

Both prompts work on your own agents at work, not just the phone question. Step 2 is the useful one to keep.

What happened when I ran step 1 three times on 19 October 2026

Same question, same morning, three tools. Three different answers.

ToolModelVerdictCalls
ChatGPTInstantApple newer, by 14 days3
CodexGPT-6.1 Sol LightSamsung newer8
Claude CodeOpus 5iPhone Duo, “came out Oct 23”5

October 23 had not happened yet. It was four days away.

Why they disagreed, and it is only in the traces. One restricted its search to site:samsung.com/news/ and named the phones it expected to find. One went hunting through regional newsrooms for models it had no reason to know about, and opened the pages to read inside them. One asked a generic question and took what came back.

And the thing step 2 found that I had missed. The Claude run cited four sources, including Apple’s own newsroom. Every one of its calls was a WebSearch. There was not a single fetch. It never opened any of them. Those citations are the search engine reporting where it found the text, not the agent reporting that it read the page.
