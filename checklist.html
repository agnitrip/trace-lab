Ship-readiness checklist

From The Green Checkmark Is Not Enough · IEEE iGET 2026 · Agni Tripathi. Made to be marked up. Take it to your next release review.

Start here

A passing score tells you the output met the check that was run. It does not tell you how the agent got there, whether the evidence it used was sound, or whether what it changed should ship. Those are separate questions, and you have to go and ask them.

1 · Grade the output

  • Accuracy — is it actually correct?
  • Groundedness — is every claim supported by something it actually retrieved?
  • Completeness — does it resolve the whole task, not most of it?
  • Actionability — can someone act on it directly, in order, safely?

In the session's capture (one model, one prompt, 8 repeats): accuracy and groundedness never moved; completeness and actionability flipped on both cases. Criteria you settle by pointing at the evidence tend to be stable. Criteria that ask "is this enough?" are judgement calls, and judgement calls move. Re-run your own judge a few times before you trust a single score.

2 · Then read the trace the part a score cannot show you

  • What did it read, and how fresh was it? Check timestamps on every source. A correct answer from a stale source passes all four criteria above and is still wrong.
  • Did it verify, or only claim to? Find the actual verification step. Confirm it ran and that it passed.
  • Did it change the thing it was judged by? Tests, fixtures, mocks, eval data, the rubric itself. Verification against something the agent authored proves only self-consistency.
  • Did any tool call fail? If so, did the run stop, or continue as if nothing happened?
  • Does the summary imply steps that never occurred? Match every claim in the final message to a real call.
  • Did it escalate when it should have? Low confidence, missing permission, ambiguous instruction, irreversible action.
  • Is the scope what you asked for? List every file, record or system it touched.

3 · Release boundaries — never ship if…

  • the agent modified its own tests, fixtures or evaluation data
  • a required verification errored and the run continued
  • a claim in the summary has no supporting tool result
  • it acted irreversibly outside the scope you granted

4 · Escalate to a human when…

  • the action is irreversible or externally visible
  • the evidence is stale, partial or conflicting
  • the agent reports low confidence, or disagrees with itself across runs
  • the failure would be expensive, unsafe or hard to detect later

5 · Is an automated judge enough here?

Usually yes — high volume, criteria you can settle against evidence, cheap and reversible errors, and you sample-audit the judge against humans on a schedule.

Not on its own — judgement-heavy criteria, irreversible or outward-facing actions, novel failure modes nobody has written a check for, and any case where the agent can influence the thing that evaluates it.

Whoever signs off owns the decision, not the dashboard. A score is evidence, not a verdict.

6 · Do these three things this month

  • Take one agent you already ship and read a full trace of it, start to finish. Just once.
  • Add one process check to your release review from section 3 above.
  • Re-run your evaluator on the same input several times and see whether it agrees with itself.
